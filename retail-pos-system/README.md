# Retail POS System — README (ສະບັບແກ້ໄຂແລ້ວ)

ລະບົບຂາຍໜ້າຮ້ານ (POS) — Backend: Node.js/Express + MongoDB (Mongoose) | Frontend: React + Vite + Tailwind

> ✅ ເອກະສານນີ້ຂຽນຫຼັງຈາກແກ້ບັນຫາຄວາມປອດໄພ ແລະ Config ທີ່ພົບໃນເວີຊັນເດີມ (ເບິ່ງລາຍລະອຽດການແກ້ໄຂຢູ່ລຸ່ມສຸດ)

---

## 1. ສິ່ງທີ່ຕ້ອງມີກ່ອນ (Prerequisites)
- Node.js 18+ (https://nodejs.org)
- MongoDB (ຕິດຕັ້ງເອງໃນເຄື່ອງ **ຫຼື** ໃຊ້ Docker — ເລືອກຢ່າງໃດຢ່າງໜຶ່ງ)
- (ຖ້າໃຊ້ Docker) Docker Desktop

`node_modules` **ບໍ່ໄດ້ລວມມາໃນໄຟລ໌ zip ນີ້ໂດຍເຈຕະນາ** — ໃຫ້ທ່ານ `npm install` ເອງໃນເຄື່ອງ ເພື່ອໃຫ້ໄດ້ native binary ທີ່ຖືກຕ້ອງກັບລະບົບປະຕິບັດການ (Windows/Mac/Linux) ຂອງທ່ານ. ຖ້າ zip ໃສ່ node_modules ມາໂດຍກົງ ມັນຈະໃຊ້ບໍ່ໄດ້ຂ້າມ OS.

## 2. ວິທີຮັນແບບພື້ນຖານ (ບໍ່ໃຊ້ Docker)

### Backend
```bash
cd backend
npm install
```

ເປີດໄຟລ໌ `backend/.env` (ມີໃຫ້ແລ້ວ) ແລະ ປັບຄ່າ:
```
PORT=5001
MONGO_URI=mongodb://localhost:27017/retail_pos
JWT_SECRET=ປ່ຽນເປັນ string ຍາວໆ ແບບສຸ່ມ (ຢ່າໃຊ້ຄ່າຕົວຢ່າງ)
```

ຖ້າ MongoDB ຢູ່ໃນເຄື່ອງທ່ານແລ້ວ (mongod ກຳລັງ run), ໃຫ້ສ້າງບັນຊີ Admin ຄົນທຳອິດ:
```bash
node seed.js
```
ຈະໄດ້ `username: admin`, `pin: 123456` — **ໃຫ້ປ່ຽນທັນທີຫຼັງ Login ຄັ້ງທຳອິດ** ຜ່ານໜ້າ "ຈັດການພະນັກງານ"

ຈາກນັ້ນເປີດ Server:
```bash
npm start
```
→ Backend ຈະຮັນຢູ່ `http://localhost:5001`

### Frontend
```bash
cd frontend
npm install
npm run dev
```
→ ເປີດ browser ໄປທີ່ URL ທີ່ Vite ບອກ (ປົກກະຕິ `http://localhost:5173`)

ຖ້າ Backend ຮັນຄົນລະ host/port, ໃຫ້ແກ້ `frontend/.env`:
```
VITE_API_URL=http://your-backend-host:5001
```

## 3. ວິທີຮັນດ້ວຍ Docker (ສະເພາະ Backend + MongoDB)

```bash
docker compose up --build
```
ຈະໄດ້:
- MongoDB ຢູ່ port `27017`
- Backend API ຢູ່ port `5001`

⚠️ **ໝາຍເຫດ**: `docker-compose.yml` ນີ້ຍັງບໍ່ໄດ້ລວມ Frontend (React) — ຕ້ອງ `cd frontend && npm run dev` ແຍກຕ່າງຫາກສະເໝີ. ຖ້າຢາກ dockerize frontend ນຳ, ຕ້ອງເພີ່ມ Dockerfile + service ໃໝ່.

ຫຼັງ container ຂຶ້ນແລ້ວ, ສ້າງບັນຊີ admin ຄັ້ງທຳອິດ:
```bash
docker exec -it pos_backend node seed.js
```

## 5. ສະຫຼຸບການແກ້ໄຂຈາກເວີຊັນເດີມ

### Backend
1. **Docker ໃຊ້ບໍ່ໄດ້ → ແກ້ແລ້ວ**: `server.js` ອ່ານ `MONGO_URI` / `PORT` / `JWT_SECRET` ຈາກ `.env` ແທນ hardcode `localhost:27017`/`5001`
2. **ບໍ່ມີ Authentication → ແກ້ແລ້ວ**: ເພີ່ມ `middleware/auth.js` (JWT verify + role check), ປ້ອງກັນທຸກ endpoint ທີ່ຄວນປ້ອງກັນ (ຂຽນ/ແກ້/ລຶບ product, category, unit, stock, employee = admin ເທົ່ານັ້ນ; ຂາຍ/ເປີດ-ປິດກະ = ຕ້ອງ login)
3. **PIN plain text → ແກ້ແລ້ວ**: hash ດ້ວຍ bcryptjs ອັດຕະໂນມັດ (Employee model pre-save hook), login ປຽບທຽບດ້ວຍ bcrypt.compare
4. **JWT secret hardcode ໃນໂຄດ → ແກ້ແລ້ວ**: ຍ້າຍໄປ `.env`
5. **ຂາຍໄດ້ເຖິງສາງຕິດລົບ → ແກ້ແລ້ວ**: ກວດ stock ພຽງພໍກ່ອນຕັດອອກໃນ `/api/orders`
6. **Image URL hardcode `localhost:5001` → ແກ້ແລ້ວ**: ເກັບເປັນ path relative (`/uploads/xxx`), frontend ຕໍ່ host ເອງຜ່ານ `resolveImageUrl()`

### Frontend
1. **Hardcode `http://localhost:5001` ຫຼາຍກວ່າ 30 ບ່ອນ → ແກ້ແລ້ວ**: ລວມສູນຢູ່ `src/api.js` (`API_BASE_URL` ອ່ານຈາກ `.env`)
2. **ບໍ່ໄດ້ບັນທຶກ Token ຕອນ Login (ໃນ `App.jsx`) → ແກ້ແລ້ວ**: ບັນຫານີ້ຮ້າຍແຮງຫຼາຍ ເພາະຫຼັງເພີ່ມ Authentication ໃນ Backend, ຖ້າບໍ່ມີ token ທຸກ API ຈະຖືກປະຕິເສດ (401) — ຕອນນີ້ບັນທຶກ ແລະ ແນບ token ໃນທຸກ request ແລ້ວ
3. ແກ້ບັນຫາ pin field ຖືກສົ່ງຄືນຈາກ backend (ຄວາມສ່ຽງດ້ານຄວາມປອດໄພ) — ຕອນນີ້ backend ບໍ່ສົ່ງ pin hash ອອກມາອີກ, ໜ້າແກ້ໄຂພະນັກງານປ່ອຍຊ່ອງ PIN ວ່າງໄວ້ໄດ້ຖ້າບໍ່ຕ້ອງການປ່ຽນ

### Docker / Deployment
1. Port/env mismatch ລະຫວ່າງ `docker-compose.yml` ແລະ `server.js` → ແກ້ໃຫ້ກົງກັນ (5001 ທັງສອງບ່ອນ)
2. ເພີ່ມ volume ສຳລັບ `uploads/` ໃຫ້ຮູບພາບບໍ່ຫາຍເມື່ອ container restart

### ຍັງເປັນຂໍ້ຈຳກັດ (ຄວນຮູ້ໄວ້)
- Docker Compose ຍັງບໍ່ລວມ frontend — ຕ້ອງ run ແຍກ
- ບໍ່ມີ rate-limiting / request validation library (ເຊັ່ນ Joi) — ຄວນເພີ່ມຖ້າຈະໃຊ້ຈິງລະດັບຮ້ານໃຫຍ່
- ຍັງບໍ່ມີ automated tests
- ຄວນປິດ CORS ໃຫ້ຈຳກັດສະເພາະ domain frontend ຕົວຈິງ ກ່ອນຂຶ້ນ production (ປັດຈຸບັນເປີດຮັບທຸກ origin)

### ອັບເດດລ່າສຸດ: ແກ້ບັນຫາ "ໜ້າຂາວ" ຕອນເຂົ້າ `/admin` ໂດຍກົງ
**ສາເຫດ**: `/admin` ເປັນ route ແຍກຕ່າງຫາກຈາກ `/` (ຄົນລະ component mount ກັນ). ຖ້າເປີດ `/admin` ໂດຍກົງ (ພິມ URL ເອງ, bookmark, ຫຼື ເປີດ tab ໃໝ່) ໂດຍທີ່ຍັງບໍ່ໄດ້ Login, ໜ້ານີ້ບໍ່ມີການກວດ token/role ຂອງຕົນເອງ — Dashboard/AdminPanel/OrdersList ຈະຍິງ API ໄປເລີຍ, backend ຕອບ `401/403` (object) ແທນ array, ພໍ code ເອົາໄປ `.filter()`/`.map()` ຈະ crash ທັນທີ ໂດຍບໍ່ຂຶ້ນຂໍ້ຄວາມຫຍັງ (React ຈະຫຍຸດ render ທັງໜ້າ = ໜ້າຂາວ)

**ແກ້ໄຂແລ້ວ**:
1. `App.jsx` — ບັນທຶກ `employee` (ບໍ່ແມ່ນແຕ່ `token`) ໄວ້ໃນ `localStorage` ຕອນ Login ນຳ, ລຶບອອກຕອນ Logout
2. `AdminPage.jsx` — ເພີ່ມການກວດ token+role ຕັ້ງແຕ່ຕົ້ນ, ຖ້າບໍ່ໄດ້ Login ຫຼື ບໍ່ແມ່ນ admin ຈະຂຶ້ນໜ້າ "ຕ້ອງ Login ກ່ອນ" ພ້ອມປຸ່ມກັບໄປ Login ແທນໜ້າຂາວ
3. `src/api.js` — ເພີ່ມ `fetchArray()` helper: ຖ້າ token ໝົດອາຍຸ (401) ຈະລ້າງ session ແລ້ວກັບໄປ Login ອັດຕະໂນມັດ, ຖ້າ response ບໍ່ແມ່ນ array ຈະສົ່ງຄືນ `[]` ແທນ crash
4. ນຳໄປໃຊ້ໃນ `Dashboard.jsx`, `AdminPanel.jsx` (ລວມ StockInModal), `OrdersList.jsx`, `EmployeeManagement.jsx`

⚠️ **ຫຼັງດຶງໂຄດຊຸດນີ້ໄປແທນ**: ຕ້ອງ **Logout ແລ້ວ Login ໃໝ່ຄັ້ງໜຶ່ງ** (ເພື່ອໃຫ້ `employee` ຖືກບັນທຶກລົງ `localStorage` — ຄົນທີ່ login ຄ້າງໄວ້ດ້ວຍໂຄດເກົ່າຈະຍັງບໍ່ມີຂໍ້ມູນນີ້)

## ອັບເດດໃໝ່: ຫົວໜ່ວຍຊື້/ຂາຍ, ລະຫັດພະນັກງານ, ແລະ Windows Service

### 1. ຫົວໜ່ວຍໃຫຍ່ (ຊື້ເຂົ້າ) vs ຫົວໜ່ວຍຍ່ອຍ (ຂາຍ) — ໜ້າ "ຈັດການສິນຄ້າ"
ຕອນເພີ່ມ/ແກ້ໄຂສິນຄ້າ ດຽວນີ້ມີ 3 ຊ່ອງໃໝ່:
- **ຫົວໜ່ວຍຍ່ອຍ** — ໃຊ້ຂາຍລູກຄ້າ (ອັນ, ແກ້ວ, ຊິ້ນ)
- **ຫົວໜ່ວຍໃຫຍ່** — ໃຊ້ຕອນຊື້ເຂົ້າຮ້ານ (ແພັກ, ແກັດ, ລັງ)
- **ອັດຕາການແປງ** — 1 ຫົວໜ່ວຍໃຫຍ່ ມີຈັກຫົວໜ່ວຍຍ່ອຍ (ຕົວຢ່າງ: 1 ແພັກ ມີ 12 ອັນ → ພິມ 12)

ຕອນ **ຮັບສິນຄ້າເຂົ້າ (Stock In)**, admin ພິມຈຳນວນເປັນ **ຫົວໜ່ວຍໃຫຍ່** (ເຊັ່ນ "ຮັບເຂົ້າ 5 ແພັກ") — ລະບົບຄິດໄລ່ ແລະ ບວກເຂົ້າ stock ເປັນ **ຫົວໜ່ວຍຍ່ອຍ** ໃຫ້ອັດຕະໂນມັດ (5 ແພັກ × 12 = 60 ອັນ ເຂົ້າ stock) — ມີຕົວເລກ preview ໃຫ້ເຫັນກ່ອນບັນທຶກ. `stock` ທີ່ນຳໄປໃຊ້ຕອນຂາຍໜ້າຮ້ານ (POS) ຍັງນັບເປັນຫົວໜ່ວຍຍ່ອຍຄືເກົ່າ, ບໍ່ກະທົບການຂາຍ.

ໜ້າ **ປະຫວັດການຮັບສິນຄ້າເຂົ້າ (Stock In History)** ດຽວນີ້ສະແດງ:
- ລະຫັດ SKU ຂອງສິນຄ້າ
- ຈຳນວນທີ່ຮັບເປັນຫົວໜ່ວຍໃຫຍ່ ພ້ອມວົງເລັບບອກຈຳນວນຫົວໜ່ວຍຍ່ອຍທີ່ໄດ້ຈິງ

⚠️ ສິນຄ້າເກົ່າທີ່ມີຢູ່ໃນ DB ກ່ອນອັບເດດນີ້ຈະຍັງບໍ່ມີ "ຫົວໜ່ວຍໃຫຍ່" ກຳນົດໄວ້ (ຈະໃຊ້ຫົວໜ່ວຍຍ່ອຍແທນຊົ່ວຄາວ) — ໃຫ້ເປີດແກ້ໄຂສິນຄ້ານັ້ນຄັ້ງໜຶ່ງແລ້ວບັນທຶກ ເພື່ອຕັ້ງຄ່າຫົວໜ່ວຍໃຫຍ່ + ອັດຕາການແປງໃຫ້ຖືກຕ້ອງ.

### 2. ລະຫັດພະນັກງານ (Employee ID) — ໜ້າ "ຈັດການພະນັກງານ"
ດຽວນີ້ລະບົບສ້າງລະຫັດພະນັກງານໃຫ້ອັດຕະໂນມັດ (ຮູບແບບ `EMP0001`, `EMP0002`, ...) ຕໍ່ຈາກເລກສູງສຸດທີ່ມີໃນຖານຂໍ້ມູນ — ບໍ່ຕ້ອງພິມເອງ. ຈະເຫັນລະຫັດຢູ່:
- ໃນ popup ຫຼັງບັນທຶກເພີ່ມພະນັກງານໃໝ່ສຳເລັດ
- ໃນຕາຕະລາງລາຍຊື່ພະນັກງານ (ຖັນ "ລະຫັດ (ID)")

⚠️ ພະນັກງານທີ່ມີຢູ່ກ່ອນອັບເດດ (ລວມທັງບັນຊີ `admin` ທີ່ສ້າງຈາກ `seed.js`) ຈະຍັງບໍ່ມີລະຫັດ (ສະແດງເປັນ "-") ຈົນກວ່າຈະເປີດແກ້ໄຂ ແລະ ບັນທຶກຄືນ (ແຕ່ລະຫັດຈະບໍ່ຖືກສ້າງໃໝ່ຕອນແກ້ໄຂ ເພາະລະບົບອອກແບບໃຫ້ສ້າງສະເພາະຕອນເພີ່ມໃໝ່ເທົ່ານັ້ນ — ຖ້າຢາກໃຫ້ພະນັກງານເກົ່າມີລະຫັດ, ຕິດຕໍ່ຂໍໃຫ້ຊ່ວຍຂຽນ script migrate ໜຶ່ງຄັ້ງໄດ້)

### 3. ຕິດຕັ້ງ Backend ເປັນ Windows Service (Auto Start/Restart)
ເພີ່ມ script ໃໝ່ 2 ອັນໃນ `backend/`: `install-service.js` ແລະ `uninstall-service.js` (ໃຊ້ package `node-windows`)

**ວິທີຕິດຕັ້ງ** (ຕ້ອງເປີດ Command Prompt ແບບ **"Run as Administrator"**):
```
cd backend
npm install
node install-service.js
```
ຫຼັງຈາກນັ້ນ Backend ຈະຮັນເປັນ Service ຊື່ `RetailPOSBackend` — ເປີດເອງທຸກຄັ້ງທີ່ເປີດ Windows, restart ອັດຕະໂນມັດຖ້າ crash, ບໍ່ຕ້ອງເປີດ terminal ຄ້າງໄວ້ອີກຕໍ່ໄປ. ກວດ/ຢຸດ/ລຶບ service ໄດ້ຈາກ Windows "Services" (ພິມ `services.msc` ໃນ Start Menu)

**ຖ້າຢາກຖອນການຕິດຕັ້ງ** (ເຊັ່ນ ຕອນຈະອັບເດດໂຄດໃຫຍ່):
```
node uninstall-service.js
```
ແລ້ວຄ່ອຍ `node install-service.js` ໃໝ່ຫຼັງອັບເດດໂຄດແລ້ວ

⚠️ ໃຊ້ໄດ້ສະເພາະ Windows ເທົ່ານັ້ນ. ແນະນຳໃຫ້ `npm run build` ໃນ `frontend/` ກ່ອນ (ໃຫ້ Backend serve ໜ້າເວັບຄົບຊຸດຈາກ service ດຽວ) ຕາມທີ່ບອກໄວ້ໃນຫົວຂໍ້ "ວິທີຮັນດ້ວຍ Docker" ຂ້າງເທິງ

### ອັບເດດລ່າສຸດ: ຟອມ "ເພີ່ມສິນຄ້າໃໝ່" ອອກແບບໃໝ່ (ນຳເຂົ້າ + ຂາຍຍ່ອຍ ໃນຟອມດຽວ)
ຕອນ **ເພີ່ມສິນຄ້າໃໝ່** (ບໍ່ແມ່ນຕອນແກ້ໄຂ) ດຽວນີ້ພິມຂໍ້ມູນ "ນຳເຂົ້າຄັ້ງທຳອິດ" ພ້ອມກັນເລີຍ:
- **ຈຳນວນນຳເຂົ້າ** + **ຊື່ຫົວໜ່ວຍໃຫຍ່** + **ລາຄານຳເຂົ້າ** (ຕໍ່ 1 ຫົວໜ່ວຍໃຫຍ່)
- **ຈຳນວນການຂາຍຍ່ອຍ** (1 ຫົວໜ່ວຍໃຫຍ່ອອກມາໄດ້ຈັກໜ່ວຍຍ່ອຍ — ຕ້ອງແກະນັບເອງ) + **ໜ່ວຍການຂາຍຍ່ອຍ** + **ລາຄາຂາຍຍ່ອຍ**

ລະບົບຄິດໄລ່ໃຫ້ອັດຕະໂນມັດ: `ສະຕັອກເລີ່ມຕົ້ນ = ຈຳນວນນຳເຂົ້າ × ຈຳນວນການຂາຍຍ່ອຍ` ແລະ `ຕົ້ນທຶນຕໍ່ໜ່ວຍຍ່ອຍ = ລາຄານຳເຂົ້າ ÷ ຈຳນວນການຂາຍຍ່ອຍ` ພ້ອມທັງບັນທຶກລົງ "ປະຫວັດການຮັບສິນຄ້າເຂົ້າ" ເປັນລາຍການທຳອິດໃຫ້ອັດຕະໂນມັດ

ຟອມ **ແກ້ໄຂສິນຄ້າ** (ສິນຄ້າທີ່ມີຢູ່ແລ້ວ) ຍັງຄືເກົ່າ — ແກ້ໄຂຄ່າປັດຈຸບັນ (ລາຄາຂາຍ, ຫົວໜ່ວຍ, ອັດຕາການແປງ, ຈຳນວນສະຕັອກ) ໂດຍກົງ ບໍ່ນັບເປັນການນຳເຂົ້າໃໝ່. ຢາກຮັບເຂົ້າສາງເພີ່ມໃຫ້ໃຊ້ປຸ່ມ "ຮັບສິນຄ້າເຂົ້າ (Stock In)" ຄືເກົ່າ

🐛 ແກ້ bug ແຝງ: ກ່ອນໜ້ານີ້ ທຸກຄັ້ງທີ່ແກ້ໄຂສິນຄ້າ ຄ່າຕົ້ນທຶນ (costPrice) ຈະຖືກຣີເຊັດເປັນ 0 ໂດຍບໍ່ຮູ້ຕົວ (ຟອມແກ້ໄຂບໍ່ໄດ້ສົ່ງຄ່ານີ້ໄປ) — ດຽວນີ້ຈະຄົງຄ່າເກົ່າໄວ້ ຖ້າຟອມບໍ່ໄດ້ສົ່ງຄ່າໃໝ່ມາ

### ອັບເດດລ່າສຸດ: ແກ້ bug SKU ຫວ່າງ + ຫົວໜ່ວຍລາຄາຕົ້ນທຶນ ຕອນແກ້ໄຂສິນຄ້າ

**1. ແກ້ bug ຮ້າຍແຮງ: ບັນທຶກແກ້ໄຂສິນຄ້າບໍ່ໄດ້ຖ້າ SKU ວ່າງ**
ຖ້າສິນຄ້າບໍ່ມີ SKU (ຊ່ອງຫວ່າງ) ແລະ ມີສິນຄ້າອື່ນທີ່ SKU ຫວ່າງຄືກັນຢູ່ແລ້ວ, ການບັນທຶກແກ້ໄຂຈະຖືກຖານຂໍ້ມູນປະຕິເສດ (error: `Cast to Number failed` ຫຼື `duplicate key`) — ດຽວນີ້ຖ້າຊ່ອງ SKU ຖືກປ່ອຍວ່າງໄວ້ຕອນແກ້ໄຂ ລະບົບຈະ**ຄົງ SKU ເກົ່າໄວ້ຄືເດີມ** ບໍ່ພະຍາຍາມບັນທຶກຄ່າຫວ່າງອີກຕໍ່ໄປ

**2. ແກ້ bug ຫົວໜ່ວຍລາຄາຕົ້ນທຶນຄາດເຄື່ອນ**
ຟອມແກ້ໄຂສິນຄ້າດຽວນີ້ໃຫ້ພິມ "ລາຄານຳເຂົ້າ" ເປັນ **ຕໍ່ 1 ຫົວໜ່ວຍໃຫຍ່** (ຄືກັນກັບຕອນເພີ່ມສິນຄ້າໃໝ່) ແຕ່ຖານຂໍ້ມູນເກັບຕົ້ນທຶນເປັນ **ຕໍ່ 1 ຫົວໜ່ວຍຍ່ອຍ** ສະເໝີ — ດຽວນີ້ລະບົບແປງຫົວໜ່ວຍໃຫ້ຖືກຕ້ອງທັງຕອນບັນທຶກ (ຫານດ້ວຍອັດຕາການແປງ) ແລະ ຕອນເປີດແກ້ໄຂຄືນ (ຄູນກັບອັດຕາການແປງ) — ເມື່ອກ່ອນຖ້າເປີດແກ້ໄຂແລ້ວບັນທຶກຄືນຫຼາຍຄັ້ງ ຄ່າຕົ້ນທຶນຈະຜິດເພື້ອນຂຶ້ນເລື້ອຍໆ (ຫຼຸດລົງເປັນອັດຕາການແປງເທົ່າທຸກຄັ້ງ), ດຽວນີ້ແກ້ໄຂແລ້ວ

**3. ຟອມແກ້ໄຂສິນຄ້າ ດຽວນີ້ໃຊ້ Layout ດຽວກັນກັບຟອມເພີ່ມສິນຄ້າໃໝ່** (ຈາກ Option B ທີ່ໄດ້ຄວາມເຫັນຮ່ວມກັນ) — ຄ່າຕ່າງໆຍັງແກ້ໄຂໂດຍກົງ (ບໍ່ນັບເປັນການນຳເຂົ້າໃໝ່, ບໍ່ຄູນຊ້ຳ) ແຕ່ Label ແລະ ລຳດັບຊ່ອງຄືກັນ ບໍ່ສັບສົນ, ມີກ່ອງ preview ສະຫຼຸບໃຫ້ເຫັນຄືກັນ

**4. ຂໍ້ຄວາມ Error ຊັດເຈນຂຶ້ນ** — ຖ້າບັນທຶກສິນຄ້າບໍ່ສຳເລັດ (ເຊັ່ນ SKU ຊ້ຳ) ຈະບອກເຫດຜົນຈິງ ແທນ "ເກີດຂໍ້ຜິດພາດ" ແບບທົ່ວໄປ
